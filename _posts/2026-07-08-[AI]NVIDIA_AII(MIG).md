# MIG (Multi-Instance GPU) 상세 설명

## 1. MIG란 무엇인가

**MIG(Multi-Instance GPU)**는 **하나의 물리적 GPU를 여러 개의 완전히 격리된 "가상 GPU 인스턴스"로 분할**하는 하드웨어 레벨 기술입니다. NVIDIA **Ampere 아키텍처(A100)**에서 처음 도입되었고, **Hopper 아키텍처(H100)**에서 기능이 강화되었습니다.

**핵심 개념**: 소프트웨어 가상화(vGPU)와 달리, MIG는 **하드웨어 자체를 물리적으로 분할**합니다.

```
[분할 전: A100 전체]
┌─────────────────────────────┐
│   1개의 물리 GPU 전체 사용    │
│   컴퓨팅 코어 100% + 메모리 80GB 전체 │
└─────────────────────────────┘

[MIG 적용 후]
┌───────┬───────┬───────┬───────┐
│Instance│Instance│Instance│Instance│
│  1     │  2     │  3     │  4     │
│(전용    │(전용    │(전용    │(전용    │
│ 코어+   │ 코어+   │ 코어+   │ 코어+   │
│ 메모리)  │ 메모리)  │ 메모리)  │ 메모리)  │
└───────┴───────┴───────┴───────┘
```

## 2. 왜 MIG가 필요한가 (도입 배경)

**문제 상황**: LLM 추론(inference)이나 소규모 개발 작업은 전체 GPU 성능이 필요 없는 경우가 많습니다. 하지만 기존 방식(시분할, Time-Slicing)에서는:
- 여러 사용자/작업이 GPU를 **시간 순서대로 나눠서** 사용
- 한 작업이 느려지면 다른 작업도 대기해야 함 (Noisy Neighbor 문제)
- 메모리 오류나 크래시가 GPU 전체에 영향을 줄 수 있음

**MIG의 해결책**: 컴퓨팅 코어와 메모리를 **물리적으로 파티셔닝**하여 각 인스턴스가 서로 완전히 독립적으로 작동하도록 보장합니다.

## 3. 코어 슬라이스(Core Slice)의 동작 원리

### 3-1. GPU 내부 구조의 기본 단위: GPC

A100/H100 같은 GPU는 내부적으로 **GPC(GPU Processing Cluster)**라는 단위로 구성됩니다. 하나의 GPC 안에는 여러 개의 **SM(Streaming Multiprocessor)**이 포함되어 있고, SM이 실제 연산(CUDA 코어, Tensor 코어 연산)을 수행하는 최소 단위입니다.

```
GPU 전체
 └─ GPC 0 ─ SM, SM, SM ...
 └─ GPC 1 ─ SM, SM, SM ...
 └─ GPC 2 ─ SM, SM, SM ...
 ...
 └─ GPC 7 ─ SM, SM, SM ...
```

**MIG의 "슬라이스(Slice)"란**: MIG는 이 GPC들을 몇 개씩 묶어서 하나의 독립된 "컴퓨팅 슬라이스"로 지정합니다. 예를 들어 `1g`(1/7 슬라이스)는 GPC 1개 묶음, `2g`(2/7 슬라이스)는 GPC 2개 묶음에 해당하는 컴퓨팅 자원을 의미합니다.

### 3-2. 물리적 격리가 이루어지는 방식

각 슬라이스는 단순히 "스케줄링 순서"로 나뉘는 게 아니라, 다음이 하드웨어 수준에서 물리적으로 분리됩니다:

| 분리 요소 | 설명 |
|---|---|
| **SM (연산 코어)** | 특정 GPC/SM 그룹이 해당 인스턴스에 전용 할당 → 다른 인스턴스와 연산 자원 공유 없음 |
| **L2 캐시 슬라이스** | GPU의 L2 캐시도 파티션 단위로 분리되어 인스턴스 간 캐시 오염(cache pollution) 방지 |
| **메모리 컨트롤러 & HBM 크로스바** | 메모리 대역폭 자체가 슬라이스별로 분리 → 한 인스턴스가 메모리를 몰아써도 다른 인스턴스 성능에 영향 없음 |
| **NVDEC/JPEG 등 미디어 엔진** | 최신 세대에서는 미디어 엔진까지 인스턴스별 전용 할당 가능 |

이 구조 덕분에 한 인스턴스에서 크래시나 ECC 메모리 오류가 발생해도 **물리적 전기 신호 경로 자체가 분리**되어 있어 다른 인스턴스는 전혀 영향을 받지 않습니다. 이것이 소프트웨어 시분할(단순히 "차례를 기다리는" 방식)과의 근본적 차이입니다.

## 4. 명령어 (시험 핵심)

### MIG 모드 활성화/비활성화
```bash
# GPU 0번에 MIG 모드 활성화
nvidia-smi -i 0 -mig 1

# 비활성화 (원래 상태로 복귀)
nvidia-smi -i 0 -mig 0
```
⚠️ **주의**: MIG 모드 전환은 **GPU 리셋이 필요**합니다 (즉시 반영되지 않고, 재부팅 또는 GPU reset 필요).

### GPU 인스턴스(GI) 생성 확인 및 조회
```bash
# 사용 가능한 MIG 프로파일 확인
nvidia-smi mig -lgip

# GPU 인스턴스 생성 (예: 1g.10gb 프로파일)
nvidia-smi mig -cgi 1g.10gb -C

# 현재 생성된 인스턴스 목록 확인
nvidia-smi mig -lgi
```

### 🔍 `-cgi` 옵션 상세 설명

**`-cgi`는 "Create GPU Instance"의 축약어**입니다. MIG 모드가 활성화된 GPU 위에 실제로 **GI(GPU Instance)**를 생성하는 핵심 명령입니다.

**전체 구조 이해하기**:
```
물리 GPU (MIG 모드 활성화)
   └─ GI (GPU Instance)          ← -cgi로 생성하는 단위
        └─ CI (Compute Instance)  ← -cci로 생성하는 단위 (또는 -C로 자동 생성)
```

MIG는 실제로 **2단계 계층 구조**로 되어 있습니다:
1. **GI (GPU Instance)**: SM 슬라이스 + 메모리 슬라이스를 함께 묶은 "하드웨어 파티션" 단위
2. **CI (Compute Instance)**: GI 내부에서 컴퓨팅 자원을 다시 세분화하는 논리적 단위 (하나의 GI 안에 여러 CI를 만들 수도 있음)

**명령어 문법 분해**:
```bash
nvidia-smi mig -cgi 1g.10gb -C
        │      │    │        │
        │      │    │        └─ CI(Compute Instance)를 GI 생성과 동시에 자동으로 함께 생성
        │      │    └─ 프로파일 이름 (1/7 슬라이스 + 10GB 메모리)
        │      └─ Create GPU Instance 옵션
        └─ MIG 서브커맨드 진입
```

**옵션 세부 사용법**:

| 명령 예시 | 동작 |
|---|---|
| `nvidia-smi mig -cgi 1g.10gb` | GI만 생성 (CI는 별도로 `-cci`로 생성해야 함) |
| `nvidia-smi mig -cgi 1g.10gb -C` | GI 생성과 동시에 **동일한 크기의 CI를 자동 생성** (실무에서 가장 많이 쓰는 방식) |
| `nvidia-smi mig -cgi 1g.10gb,1g.10gb,2g.20gb -C` | **여러 프로파일을 콤마로 구분해 한 번에 다중 생성** |
| `nvidia-smi mig -cgi 9,9,14 -C` | 프로파일 이름 대신 **Profile ID**(숫자)로 지정 가능 (`-lgip`로 조회한 ID 사용) |
| `nvidia-smi mig -i 0 -cgi 1g.10gb -C` | `-i 0`으로 **GPU 인덱스를 먼저 지정**한 뒤 해당 GPU에만 생성 (멀티 GPU 서버에서 필수) |

⚠️ **시험/실무 포인트**:
- `-C`(대문자)를 붙이지 않으면 GI만 만들어지고 **아직 사용 가능한 상태가 아닙니다**. CI가 있어야 실제로 CUDA 컨텍스트를 그 인스턴스에 붙일 수 있기 때문에, 실무에서는 거의 항상 `-C`를 함께 사용합니다.
- 생성 가능한 프로파일 조합은 GPU의 **남은 슬라이스 용량**에 따라 제한됩니다. 예를 들어 이미 `3g.40gb`를 하나 만들었다면, 남은 4/7 슬라이스 내에서만 추가 생성이 가능합니다.
- 생성된 GI/CI는 `nvidia-smi mig -lgi`(GI 목록), `nvidia-smi mig -lci`(CI 목록)로 확인하며, 삭제는 `-dci`(Destroy CI), `-dgi`(Destroy GI) 옵션을 사용합니다.

### 컨테이너에서 특정 MIG 인스턴스 사용
```bash
docker run --gpus '"device=0:0"' ...   # GPU 0번의 MIG 인스턴스 0번 지정
```

## 5. A100 / H100의 MIG 분할 옵션 및 최대 인스턴스가 "7개"인 이유

| GPU | 최대 인스턴스 수 | 대표 프로파일 |
|---|---|---|
| A100 (80GB) | 최대 7개 | 1g.10gb, 2g.20gb, **3g.40gb**, 7g.80gb |
| H100 (80GB) | 최대 7개 | 1g.10gb, 2g.20gb, **3g.40gb**, 7g.80gb (2세대 MIG 엔진, 성능 향상) |

3g.40gb가 30GB가 아닌 이유는, 컴퓨팅 슬라이스(GPC)는 1개 단위로 세밀하게 나뉘지만, 메모리는 L2 캐시 크로스바의 설계 제약으로 1-2-4-8개 단위로만 그룹화가 가능하기 때문입니다. 3개 컴퓨팅 슬라이스를 쓰려면 메모리도 그에 맞는 그룹 단위가 필요한데, 3슬라이스 그룹이 지원되지 않아 그 다음 단위인 4슬라이스(=40GB)로 올림 처리된 것입니다. 이게 바로 3g와 4g가 동일한 메모리 용량(40GB)을 갖게 되는 이유이기도 합니다.

### 왜 "7"이라는 숫자가 나오는가?

**① GPC 물리 구조 기반**
A100/H100 다이(die)는 물리적으로 **8개의 GPC**로 설계되어 있습니다. 하지만 MIG 슬라이스 분할에는 이 중 **7개만 사용 가능한 연산 슬라이스로 노출**됩니다. 나머지 1개 분량의 자원은 다음 용도로 예약되어 있어 사용자 인스턴스로 분할되지 않습니다:
- 칩 제조 과정의 **수율(yield) 방어용 여분(redundancy)** — 일부 GPC에 결함이 있어도 정상 동작하도록 하는 여유분
- GPU 내부 관리/모니터링을 위한 시스템 예약 자원

이 때문에 "물리적으로는 8슬라이스에 대응하는 다이 구조지만, MIG로 쪼갤 수 있는 유효 슬라이스는 7개"가 되는 것입니다.

**② 메모리 슬라이스도 동일한 논리로 8분할 → 7개 노출**
HBM 메모리 컨트롤러 역시 8개 채널 구조로 설계되어 있으나, 마찬가지로 1개 채널 분량은 예약되고 **7개 슬라이스**만 `1g.10gb`처럼 사용자에게 프로파일로 제공됩니다. (80GB ÷ 8 = 10GB 단위, 여기서 7개 슬라이스가 최대 조합의 기준이 됨)

**③ 프로파일 조합도 "7"을 기준으로 계산됨**
- `1g.10gb` × 7개 = 최대 7개 인스턴스 (가장 작은 단위로 최대 분할)
- `2g.20gb` × 3개 (6/7 슬라이스 사용, 1슬라이스는 미사용) 또는 조합 방식
- `7g.80gb` × 1개 = MIG를 켰지만 실질적으로 전체 GPU를 통짜로 쓰는 것과 유사한 최상위 프로파일

즉 "7"은 임의로 정해진 숫자가 아니라, **다이 설계상 8개 GPC 중 수율/예비용 1개를 제외한 실사용 가능 슬라이스 개수**에서 유래한 하드웨어적 제약입니다.

## 6. MIG 사용 적합/부적합 시나리오

| 적합한 경우 | 부적합한 경우 |
|---|---|
| 소규모 추론 서빙 (다중 모델 동시 서빙) | 대규모 분산 학습 (멀티노드 all_reduce) |
| 멀티테넌트 클라우드/연구랩 (사용자별 격리) | NVLink 기반 GPU 간 통신이 필요한 작업 |
| 결정론적 성능이 중요한 프로덕션 추론 | 단일 대형 모델을 여러 GPU에 걸쳐 학습 |

⚠️ **시험 포인트**: MIG로 분할된 인스턴스들은 **NVLink로 서로 통신하지 않습니다**. 따라서 대규모 학습(NCCL all_reduce 등)에는 MIG를 사용하지 않고, **전체 GPU 모드**로 되돌려서 사용해야 합니다.

⚠️ **시험 포인트**: "이 GPU가 MIG 인스턴스를 몇 개까지 지원하는가"를 물을 때는 **Ampere/Hopper/Blackwell 세대의 데이터센터급 GPU(A100, A30, H100, H200 등)**로 제한된다는 것을 기억하시면 됩니다. RTX나 T4 같은 GPU는 지원하지 않습니다.

## 7. 문제(Q27)와 연결되는 핵심 포인트

Q27에서 "fixed share scheduler로 변경"하는 문제의 정답이 `nvidia-smi -i 0 -mig 1`인 이유는:
- MIG 모드 자체가 **하드웨어 레벨의 고정 분할(Fixed Share)** 방식이기 때문
- 오답 선택지(`esxcli` 명령들)는 **VMware ESXi 전용 vGPU 스케줄링 명령**이며, 이는 **소프트웨어 시분할 스케줄러**(vGPU 스케줄링 정책 - Best Effort/Equal Share/Fixed Share, Q47 참고)와 관련된 것으로 MIG와는 다른 계층의 기술입니다.

### 📌 헷갈리기 쉬운 개념 구분

| 기술 | 계층 | 격리 수준 |
|---|---|---|
| **MIG** | 하드웨어 (베어메탈 GPU 분할, GPC 단위) | 물리적 완전 격리 |
| **vGPU (VMware ESXi)** | 하이퍼바이저 소프트웨어 | 시분할(Time-Slice), Q47의 `RmPVMRL` 관련 |
| **Docker `--gpus device=`** | 컨테이너 런타임 | GPU 전체를 컨테이너에 노출 (분할 아님) |
